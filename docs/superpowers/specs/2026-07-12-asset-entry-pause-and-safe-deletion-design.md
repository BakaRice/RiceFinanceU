# 资产暂停录入与安全删除设计

## 背景

RiceFinanceU 是资产快照账本。资产一旦进入快照，就已经成为历史账本的一部分，不能通过删除资产来抹除。现有 `isActive` 同时表达“停用”“软删除”和“是否参与录入”，语义混杂，而且会让停用资产从总资产计算中消失。

本次调整把“是否参与日常录入”与“是否存在”分开：已记录资产始终存在，只能在正常录入和暂停录入之间切换；从未进入任何快照的错误资产可以永久删除。

## 领域语言

### 正常录入资产

正常出现在快照录入页的资产。用户可以在新快照中更新它的金额、收益和收益率。

### 暂停录入资产

暂时不出现在快照录入页，但仍属于当前资产账本的资产。系统沿用它最后一次记录的金额，并继续将其计入总资产、资产结构和历史走势。

界面统一使用“暂停录入 / 恢复录入”，不再使用“冻结”“停用”或“禁用”。

### 永久删除

只适用于从未进入任何快照的错误资产。只要存在一条引用该资产的 `SnapshotValue`，永久删除就必须失败。

### 更正快照

用于修正错误资产状态的新快照。已经进入快照的资产不能通过永久删除来抹除；如果资产不再持有，应先录入最终金额 `0`，再暂停录入。

## 方案比较

### 方案 A：显式 `entryStatus`（采用）

为资产增加 `entryStatus: 'normal' | 'paused'`。状态只回答资产是否参与日常录入，不决定资产是否存在或是否计入总资产。

优点是语义清楚，API、Web 和小程序可以共享同一判断。缺点是需要迁移现有 `isActive` 数据和所有客户端过滤逻辑。

### 方案 B：增加 `isEntryPaused`

保留 `isActive`，再增加布尔字段。改动较小，但会形成两个容易冲突的状态源，后续仍需解释“inactive + not paused”等无效组合。

### 方案 C：继续复用 `isActive`

只改界面文案。实现最少，但无法消除停用、暂停录入和软删除之间的语义冲突，也无法安全表达永久删除，因此不采用。

## 数据模型与迁移

`Asset` 使用：

```ts
entryStatus: 'normal' | 'paused'
```

新建资产默认是 `normal`。

读取旧数据时：

- 已有合法 `entryStatus` 时直接保留。
- 缺少 `entryStatus` 且 `isActive !== false` 时迁移为 `normal`。
- 缺少 `entryStatus` 且 `isActive === false` 时迁移为 `paused`。
- 规范化后的新数据不再依赖 `isActive`。

已核对线上数据：旧停用黄金资产 `b931c351-9db0-4567-9223-9c63daf5094f` 没有任何快照引用，可以在新删除规则部署后永久删除。另一项正常黄金存在 7 条快照引用，必须保留。

导入兼容旧备份中的 `isActive`，导出使用新的 `entryStatus`。

## 录入与统计行为

- 快照录入页只展示 `entryStatus === 'normal'` 的资产。
- Worker 只接受正常录入资产的显式快照提交。
- 暂停录入资产不会出现在提交表单中，由快照补全逻辑沿用上一份快照值。
- 总览、资产结构、对比和趋势使用全部仍存在的资产，不再按录入状态排除暂停资产。
- 定投管理不展示暂停录入资产，因为暂停状态表示近期不进行额外投资或清仓动作。
- 资产管理页继续展示正常和暂停录入资产，并允许随时恢复录入。

如果所有资产都暂停录入，用户不需要创建没有变化的新快照；现有“至少提交一项资产值”的校验保持不变。

## API 设计

### 暂停与恢复

继续使用：

```http
PATCH /api/assets/:id
```

请求体包含：

```json
{ "entryStatus": "paused" }
```

或：

```json
{ "entryStatus": "normal" }
```

Worker 拒绝其他状态值。

### 永久删除

使用：

```http
DELETE /api/assets/:id
```

请求体必须包含当前资产完整名称：

```json
{ "confirmName": "黄金" }
```

Worker 按顺序校验：

1. 资产存在。
2. `confirmName` 与资产名称完全一致。
3. `snapshotValues` 中不存在该资产 ID。

满足条件后，Worker 从 `assets` 中永久移除该资产。存在历史引用时返回 `409 Conflict`，错误码为 `ASSET_HAS_SNAPSHOT_HISTORY`；名称不匹配时返回 `400 Bad Request`。

后端检查是最终安全边界，不能只依赖前端确认弹窗。

## 界面设计

### 资产管理页

- 状态列只提供“正常录入 / 暂停录入”。
- 更多操作根据状态显示“暂停录入”或“恢复录入”。
- 永久删除入口始终可见，但历史资产点击后会在服务端检查时被拒绝，并提示“该资产已有历史快照，只能暂停录入”。
- 暂停录入行使用弱化样式，但不显示为删除或失效。

### 删除双重确认

第一次提醒：

- 标题：“永久删除资产”
- 说明操作不可恢复，且只允许删除从未进入快照的资产。
- 操作：“继续删除 / 取消”

第二次提醒：

- 显示资产完整名称。
- 要求用户输入完整资产名称。
- 只有完全匹配时“永久删除”按钮才可用。

### 资产详情页

使用相同的暂停、恢复和永久删除规则，不保留旧“停用”入口。

### 小程序

资产管理和录入页使用同一 `entryStatus` 语义。小程序提供暂停、恢复和双重确认后的安全永久删除，不能继续调用旧软删除行为。

## 错误处理

- 非法 `entryStatus`：返回 400，不写入数据。
- 名称确认不匹配：返回 400，不写入数据。
- 资产存在历史引用：返回 409，不写入数据。
- 删除或状态更新失败：客户端保留当前页面数据并显示明确错误。
- 旧备份迁移失败：数据检查页指出具体资产，不静默删除资产。

## 测试与验证

### 领域和 Worker

- 旧 `isActive` 到 `entryStatus` 的兼容迁移。
- 新资产默认正常录入。
- 暂停资产不能显式提交新快照值。
- 暂停资产的旧值可以被快照补全逻辑沿用。
- 无历史资产在名称匹配时可永久删除。
- 名称不匹配时不能删除。
- 存在任何快照引用时返回 409 且数据不变。
- 导入导出保留新状态并兼容旧备份。

### Web

- 录入页隐藏暂停录入资产。
- 总览继续计算暂停录入资产。
- 资产页可暂停和恢复。
- 双重确认在第二步名称匹配前不能提交。
- 历史资产删除失败时展示正确提示。

### 小程序

- 录入页隐藏暂停录入资产。
- 总览仍包含暂停录入资产。
- 暂停、恢复和删除调用新的 API 语义。

### 完成检查

运行：

```bash
npm run test
npm run build
npm run mini:test
```

部署后检查 `/api/health`，再通过永久删除 API 删除已核对的无引用旧黄金资产，并重新读取资产列表和快照引用确认结果。

## 不在本次范围

- 不增加交易流水或会计分录系统。
- 不自动创建负数“红冲”交易。
- 不修改或删除已有快照的历史值。
- 不增加批量永久删除。
- 不让暂停状态影响资产估值、汇率或趋势计算。
